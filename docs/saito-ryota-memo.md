## 4. 判断の記録（なぜこうなっているか）

| 決めたこと | 理由 | 検討したほかの案・メモ |
|---|---|---|
| 仮予約 → スタッフ承認 → 確定の2段階にする | スペース・人数・時間の組み合わせで受けられるかは、人が見て決めたほうが確実。システムを単純にできる | 自動確定は在庫管理が必要になるので見送り |
| 空き状況は「1日の確定人数が15人未満なら○」の粗い目安 | 最初は「確定が1件でもあればその日は×」だったが、1日に複数組を受けたいので定員制にした（9/17）。厳密な判定はスタッフに任せる | スペース別・時間帯別の判定はしない |
| 空き状況はスプレッドシートだけで判定し、カレンダーは確定の記録先にする | カレンダーの共有権限待ちで開発が止まった（9/07）。シートだけで完結させればカレンダーの不調で予約受付が止まらない | カレンダーは権限が届いた後に「書き込み専用」で復活（9/14） |
| カレンダー登録・LINE・メールが失敗しても確定は続行 | 外部サービスの一時的な不調で予約が確定できないほうが困る。失敗はDiscordで知らせて人が補う | |
| GASは会社アカウントのプロジェクトで動かす | 個人アカウントだとメールの差出人・権限・引き継ぎが個人に依存する（9/17） | 所有者が退職などで使えなくなると全部止まるので注意（7章） |
| LINEのトークンはチャネルID/シークレットから都度取得 | 長期トークンの発行には、Developers Consoleでプロバイダーの権限が必要だった。ID/シークレットだけなら社長から受け取れた | `LINE_CHANNEL_ACCESS_TOKEN` を設定すればそちらが優先される |
| 氏名のカタカナ入力は「案内」だけで強制しない | 漢字で入れた人が送信できず離脱するのを防ぐ（9/17） | 列名は「氏名（カタカナ）」のまま |
| 社外スタッフはメールのログインリンクで本人確認 | 「自分として実行」のWebアプリでは、同じWorkspaceドメイン以外のメールアドレスが取れない（Googleの仕様） | 別デプロイ（「アクセスしているユーザーとして実行」）は、予約受付と両立しないので見送り。デプロイは1つのまま |
| 承認リンクは権限チェックなし | Discordのチャンネルにいるスタッフがスマホからすぐ承認できることを優先。予約IDはUUIDで推測できない | キャンセル済みは承認できないようにした（2026-11-10） |
| Discordに電話番号・メールを載せない | Discordはスタッフ以外も入りうる・端末に残る。個人情報は管理画面で見る（10/16） | |
| 日曜・祝日は予約フォームでは受けないが、管理画面からは登録できる | 定休日でも特別対応（貸切など）をすることがあるため | |
| 予約は3か月先まで | 先の予定を受けたい要望に合わせて拡大（11/09） | `BOOKING_MONTHS_AHEAD` で変更可能 |
| 管理画面からの仮予約登録ではお客様に受付メールを送らない | 受付メールの文面が「LINEでご連絡します」だが、代理登録はLINE連携がない | |
| 人数変更でお客様に通知しない | お客様からの依頼で変える想定。スタッフが直接やり取りしている | |
| 保守用の関数にガードを付け、名前の末尾に `_` を付けない | 末尾 `_` にするとGASエディタの関数一覧から消えて実行できなくなるため | 17章（developer-spec） |

## 5. ハマりどころと結論

時間を使った順。同じことでまた悩まないように。

### 5.1 LINEのuserIdはプロバイダーごとに違う（最大のハマりどころ）

- **症状**: 本番でLINE通知だけが `status=400 {"message":"Failed to send messages"}` で失敗。お客様（テストユーザー）は `@186lmmed` を友だち追加済みで、リッチメニューも見えていた
- **調べたこと**: `debugLineBotInfo()` でチャネルは正しく `@186lmmed` を指していた。`debugLineFriendStatus()`（`GET /v2/bot/profile/{userId}`）が `404`
- **原因**: LIFFを置いたLINE Loginチャネル「oO SPACE予約」が、`@186lmmed` のMessaging APIチャネルと**別のプロバイダー**だった。userIdはプロバイダーごとに別の値なので、LIFFで取ったuserIdは `@186lmmed` から見ると「知らない人」
- **間違えた判断**: 最初は「リンクされたLINE公式アカウント」の設定は友だち追加のUXだけの機能だから、プロバイダーが違っても問題ないと考えていた。プロンプトについては正しいが、userIdが一致しないので通知は原理的に届かない
- **結論**: LIFFは必ず**Messaging APIチャネルと同じプロバイダー**のLINE Loginチャネルに作る。作り直したら `LIFF_ID` を更新し、リッチメニューのリンク先も差し替える
- **残る影響**: 旧LIFFで申し込まれた予約のuserIdには通知が届かない

### 5.2 社外アカウントでは管理画面に入れない

- `Session.getActiveUser().getEmail()` は、「自分として実行」のWebアプリでは**スクリプト所有者と同じWorkspaceドメインのユーザーにしか**メールアドレスを返さない。Gmailだと空文字
- GASプロジェクトを共有しても変わらない（2026-10-05に実機で確認）
- 結論: メールのログインリンク方式を作った

### 5.3 `ScriptApp.getService().getUrl()` のURLが社外の人に開けない

- 実際には開けないURLや、`/a/macros/sinnovation.jp/` 形式（社内ドメイン限定）のURLを返すことがある
- 結論: 「デプロイを管理」に表示される `https://script.google.com/macros/s/〜/exec` をスクリプトプロパティ `WEB_APP_URL` に入れる

### 5.4 GASへのPOSTがCORSで失敗する

- `Content-Type: application/json` で送るとブラウザがプリフライト（OPTIONS）を送り、GASが処理できずに失敗する
- 結論: `text/plain;charset=utf-8` でJSON文字列を送り、GASで `JSON.parse(e.postData.contents)`

### 5.5 電話番号の先頭の0が消える

- `09012345678` をそのままシートに書くと数値 `9012345678` になる
- 結論: `sanitizeCell_()` で `0`始まりの数字列に `'` を付ける。過去データは `fixPhoneNumberLeadingZeros()` で修正（実行したかは未確認、6章）

### 5.6 「日本の祝日」カレンダーに祝日でない日が入っている

- 2024年頃から節分・ひな祭り・七五三・クリスマスなども同じカレンダーに載るようになった
- 結論: 説明欄が「祝日」で始まるものだけを祝日にする。Google側の書き方が変わったらまた壊れる可能性がある

### 5.7 Discord通知が届かない

- Slack形式（`{text}`）でDiscordに送ると「空のメッセージ」として400になる。古い形式の `discordapp.com` のURLをDiscordと判定できていなかった
- 2000文字を超えると400
- 結論: 両方のドメインをDiscord扱いにし、長文は切り詰める。`debugDiscordWebhook()` で原因が分かるようにした

### 5.8 キャンセルしてもカレンダーの予定が残る

- 当初は確定時にイベントIDを保存していなかった
- 結論: 「カレンダーイベントID」列を追加し、キャンセル時に削除する

### 5.9 管理画面の通信エラー

- 1つのブラウザで複数のGoogleアカウントにログインしていると、`google.script.run` が失敗することがある（GASの既知の問題）
- 結論: シークレットウィンドウで開いてもらう。ログイン画面のエラーにも案内を出している

### 5.10 `clasp push` しても本番が変わらない

- `push` は最新コードを更新するだけで、本番の `/exec` はデプロイしたバージョンで動く
- 新しいデプロイを作るとURLが変わり、フロントの `GAS_ENDPOINT_URL` や過去の承認リンクが全部使えなくなる
- 結論: 既存のデプロイIDを指定して `clasp deploy --deploymentId …`

### 5.11 保守用の関数が誰でも呼べてしまう

- 「全員（匿名含む）」で公開しているので、承認画面などを開けば開発者ツールから末尾 `_` でないトップレベル関数を所有者の権限で呼べる（`sendReminders` を連打される、`checkConfig` で設定が漏れる、など）
- 結論: `assertEditorRun_()` / `assertEditorOrTriggerRun_()` のガード。トリガー経由の判定は `triggerUid` の照合に頼っていて、**本番での動作が未確認**（6章）

## 9. Claude Codeでの開発の進め方

この開発はほぼすべてClaude Code（Claude）に依頼して進めてきました。

- `CLAUDE.md` はClaude Codeが毎回自動で読む。ルール・設計の要点・引き継ぎメモをここに書いておくと、毎回説明しなくて済む。**設計を変えたら `CLAUDE.md` も更新する**（Claudeに「CLAUDE.mdも更新して」と頼めばよい）
- `TASKS.md` のPhase順に、1フェーズずつ依頼 → 動作確認 → 次、で進めた。一度に複数のことを頼むより、1つずつのほうが確認しやすい
- 作業ブランチは `claude/〇〇`。PRを作ってもらい、内容を見てmainにマージする
- ClaudeはGASエディタ・LINE Developers・Discord・GitHub Pagesの設定画面は操作できない。**スクリプトプロパティの登録、`clasp deploy`、トリガー登録、実機での確認は人がやる**
- 実機でしか分からない問題（LINEのプロバイダー問題など）は、診断用の関数（`debugLine*` など）を作ってもらい、GASエディタで実行してログを貼り付けて相談すると早い
- 「開発者ツールから呼べる関数」のルール（`CLAUDE.md`）を守ってもらうよう、新しい関数を追加するときは確認する
